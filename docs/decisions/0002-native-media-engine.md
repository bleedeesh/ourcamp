# 0002. Tauri 2 + React, медиа в Rust

**Дата:** 2026-10-27 · **Статус:** принято

## Контекст
Требования: максимальная производительность, чистый звук, стабильный битрейт,
громкость каждого участника и стрима отдельно. Программа весь вечер работает фоном
рядом с играми.

## Решение
- Оболочка — **Tauri 2** (системный webview + Rust), UI — **React + TypeScript**.
- **Весь звук и видео — в Rust**: захват, обработка (AEC3/шумодав/AGC), WebRTC
  (LiveKit Rust SDK поверх libwebrtc), микширование (`oc-audio`), вывод (`cpal`),
  отрисовка стрима (`wgpu`, отдельное окно).
- Webview получает только команды и события (уровни ≈20 Гц), аудио через IPC не ходит.

## Почему
- Так устроен Discord: веб-интерфейс + нативный C++ медиадвижок на libwebrtc. Это даёт
  собственную регулировку громкости и обход системного приглушения Windows
  («ducking» при использовании устройства связи).
- WebRTC внутри системных webview ненадёжен: в WebKitGTK (Linux) он требует патчей,
  в WKWebView (macOS) были проблемы с `getDisplayMedia`. Нативный движок одинаков на всех ОС.
- Tauri: установщик и память в разы меньше, чем у Electron (десятки МБ против сотен) —
  важно для фоновой программы.

## Отвергнуто
- **Electron + livekit-client (JS).** Быстрее старт (голос за пару недель), Chromium
  одинаков везде. Минусы: 150–300 МБ памяти, звук ограничен возможностями браузера,
  громкость через Web Audio. Остаётся запасным планом, если в M1/M2 сборка libwebrtc
  окажется неподъёмной: UI и сервер при переходе не меняются.
- **Нативный UI (Qt/egui).** Медленнее разработка интерфейса, хуже знакомый стек.

## Последствия
- Нужен Rust; медиаядро — самая сложная часть проекта (M2).
- Интерфейс `VoiceEngine` в TS — единственная граница UI↔движок; `DemoEngine` позволяет
  верстать в браузере.
