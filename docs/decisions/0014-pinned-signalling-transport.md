# 0014. Пиннинг сертификата для LiveKit через свой транспорт сигнализации

**Дата:** 2026-10-27 · **Статус:** принято (реализация — M3)

## Контекст
ADR-0005: у сервера лагеря нет домена и сертификата от УЦ; клиент доверяет ровно тому
сертификату, чей SHA-256 записан в ссылке (`fp`). API лагеря клиент вызывает сам, но
WebSocket сигнализации LiveKit открывает SDK, а `livekit` 0.9.7 по умолчанию собран
вообще без TLS (только `ws://`).

## Решение
- В `livekit-net` (зависимость SDK) есть подключаемый транспорт: трейты `WsClient` /
  `HttpClient` и `set_ws_client` / `set_http_client`. Клиент OurCamp регистрирует
  **свой** транспорт при старте: WebSocket (`tokio-tungstenite`, уже в дереве SDK) поверх
  `rustls` с собственным `ServerCertVerifier`, который сравнивает SHA-256 сертификата
  с ожидаемым отпечатком.
- Отпечатки — в реестре «`host:port` → `fp`», заполняется из ссылки лагеря перед
  подключением. **Неизвестный хост — отказ** (fail closed), в том числе `ws://` без TLS
  (кроме `127.0.0.1` в debug-сборке — локальный LiveKit из Docker).
- Тот же верификатор используется для HTTPS-запросов к API лагеря.
- `livekit-net` подключается напрямую с версией **ровно** как у SDK (`=0.1.4`): вторая
  копия крейта — это второй, пустой реестр, и транспорт молча не применится. Тест
  проверяет, что SDK видит зарегистрированный клиент (`has_ws_client`).

## Почему это защищает и звук
Ключи DTLS медиаканала (отпечатки в SDP) приходят по сигнализации. Сигнализация
закреплена за сертификатом лагеря → подменить медиа нельзя, даже если UDP идёт напрямую.

## Отвергнуто
- **Фича `rustls-tls-native-roots`** — доверяет системным УЦ, самоподписанный
  сертификат не пройдёт, а «принять любой» — это отсутствие защиты.
- **Форк SDK** — сопровождать libwebrtc-обвязку самим ради одного верификатора.

## Последствия
- Регистрация разовая на процесс (`OnceLock`): транспорт ставится в `lib.rs` до первого
  подключения, реестр отпечатков меняется на лету.
- При обновлении `livekit` сверять версию `livekit-net` и трейты транспорта.
