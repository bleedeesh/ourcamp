# ADR-0063: потолки битрейта стрима — равное качество в каждом режиме

Статус: принято. Заменяет таблицу из ADR-0061.

**Код:** `bitrate` в `src-tauri/src/stream/mod.rs`

## Контекст
Дима: на всех качествах нужен хороший битрейт. Значение в таблице — это потолок: при хорошем канале идёт он, при плохом столько, сколько возможно.

Так уже и работает: таблица задаёт только верхнюю границу. Реальный битрейт — меньшее из трёх чисел:
- потолка из таблицы;
- оценки WebRTC, сколько пропускает исходящий канал стримера;
- того, что нужно самой картинке: простая картинка потратит меньше потолка.

Таблица из ADR-0061 бралась по рекомендациям для загрузки видео, а не из замеров.

## Замер
RTX 3060, профиль High, низкая задержка: кодировщик NVIDIA, затем декодер Windows и сравнение яркости с исходником. Картинка — два слоя мелкого шума, движущихся навстречу, то есть намеренно тяжёлая. Три секунды, первая не считается. Средний PSNR, дБ:

| Мбит/с | 6 | 10 | 12 | 15 | 20 | 30 | 40 | 60 |
|---|---|---|---|---|---|---|---|---|
| 720p30 | **36,8** | 39,3 | | 41,5 | | | | |
| 720p60 | 33,2 | **35,8** | | 37,9 | 39,3 | | | |
| 1080p30 | | | **36,3** | | 38,8 | 40,8 | | |
| 1080p60 | 31,0 | | 32,9 | | **35,3** | 37,3 | 38,8 | |
| 1440p30 | | | | | **35,8** | 37,7 | | |
| 1440p60 | | 30,9 | | | 32,8 | 34,1 | **35,9** | 37,8 |

Точки насыщения на такой картинке нет: каждое увеличение битрейта в 1,5 раза прибавляет около 2 дБ, поэтому «идеального» значения замер не даёт. Но он показывает, что прежняя таблица была неравной: 1080p60 при 12 Мбит/с — это 32,9 дБ, а 1080p30 при 8 Мбит/с — 33,8 дБ.

## Решение
Потолки выбраны так, чтобы все режимы получали примерно одинаковые 35–37 дБ (жирное в таблице):

| | 30 fps | 60 fps |
|---|---|---|
| 720p | 6 Мбит/с | 10 Мбит/с |
| 1080p | 12 Мбит/с | 20 Мбит/с |
| 1440p | 20 Мбит/с | 40 Мбит/с |

Настройки для пользователя нет: выбор качества и так задаёт нужную строку.

## Отклонённые варианты
- **Таблица ADR-0061 (1080p60 — 12 Мбит/с).** Заметно хуже на тяжёлой картинке, а на лёгкой более высокий потолок ничего не стоит: лишнее не тратится.
- **Ещё выше, 38–40 дБ.** Цена — в полтора-два раза больше на зрителя, а домашний канал и так главное ограничение.

## Последствия
**Подстраивается только исходящий канал стримера.** Лагерь отправляет стрим каждому зрителю в том виде, в каком получил, simulcast нет (ADR-0049). Поэтому:
- если исходящего канала сервера не хватает на всех зрителей, стрим страдает у них, и стример об этом не узнаёт;
- зритель со слабым входящим каналом получит рывки или паузы, а не картинку похуже.

1080p60 и 3 зрителя — до 60 Мбит/с исходящего канала хозяина, 1440p60 — до 120. Окно «Начать стрим» показывает это число. На домашнем сервере с обычным каналом хозяину придётся выбирать качество ниже. Это самый заметный риск новой таблицы.

## Проверка
Настоящее приложение, 1080p60, живая страница с WebGL, стример и зритель на одной машине: запрос и отправка 20 Мбит/с ±0,2 с второй секунды и до конца минуты, ошибок разбора `h264` у зрителя нет.

Заодно выяснилось, что качели битрейта (3–17 Мбит/с с периодом 4 секунды) — особенность тестовой страницы: на чистом сдвиге неизменной картинки контроль битрейта раскачивается, а на живом содержимом поток ровный. Кодировщик менять не понадобилось.

**Не проверено при записи этой ADR.** Настоящая игра с этой таблицей и качество на глаз: PSNR на синтетической картинке показывает соотношение режимов, а не то, что увидит человек. Настоящая сеть и несколько зрителей. 1440p60 при 40 Мбит/с через всё приложение: источника такого размера в проверке не было, только кодировщик и декодер Windows.
