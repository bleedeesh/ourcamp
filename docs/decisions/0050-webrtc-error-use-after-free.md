# 0050. Ошибки WebRTC на Windows читались из освобождённой памяти

**Дата:** 2026-10-31 · **Статус:** принято
**Код:** `.cargo/config.toml`, тест `an_error_from_webrtc_is_read_while_alive` в `apps/desktop/src-tauri/src/voice/room.rs`

## Контекст
Отладочная сборка на Windows падала примерно в 15 % прогонов тестов голоса, после разрыва комнаты
сервером (`DuplicateIdentity`):

```text
unsafe precondition(s) violated: ptr::copy_nonoverlapping ... do not overlap
exit code: 0xc0000409
```

Цепочка такая:
1. Сервер разорвал соединение. SDK сам запускает `Room::close` и снимает публикации: `unpublish_track` →
   `remove_track`. Соединение к этому моменту уже закрыто, и libwebrtc возвращает ошибку
   `PeerConnection is closed.`. Это штатно, SDK эту ошибку ожидает и пропускает.
2. `webrtc-sys` превращает её в C++-исключение: `throw std::runtime_error(serialize_error(...))`.
3. `webrtc-sys` берёт макросы из сборки libwebrtc, а там, как в Chromium, `_HAS_EXCEPTIONS=0`. В таком
   режиме `std::exception` у MSVC **хранит только указатель** на текст и не копирует его. Текст лежит во
   временной `std::string`, и она уничтожается ещё до `catch`.
4. `cxx` в `catch` получает `what()`, то есть указатель на свободный блок, и копирует текст в Rust. Память
   ещё не затёрта, поэтому текст выглядит верным. Но новая строка в Rust иногда получает тот же блок, и
   тогда источник и приёмник совпадают. Отладочная проверка Rust это замечает и завершает процесс.

Как это проверено:
- Пример на чистом MSVC: с `/D_HAS_EXCEPTIONS=0` блок из `what()` снова выдаёт `malloc`, то есть он свободен.
  Со значением по умолчанию этого не происходит ни разу за 512 попыток.
- Временный зонд в `cxx` показал то же в настоящем `remove_track`.

**В release** проверки нет, поэтому процесс не падает: 20 прогонов из 20 прошли. Зонд показал, что блок был
уже свободен: в 4 вызовах из 20 копия легла прямо на источник, ещё в 15 тот же блок выдавался при следующих
выделениях. Записи в чужую память нет: копия идёт в свой новый блок, а текст ошибки SDK здесь отбрасывает.
Остаётся чтение освобождённой памяти. Другой поток может успеть занять этот блок, и тогда текст ошибки
окажется мусором. Это неопределённое поведение, хотя пользователь его не заметит.

На других платформах этого нет: `_HAS_EXCEPTIONS` есть только у MSVC.

## Решение
Собирать C++-код `webrtc-sys` с `_HAS_EXCEPTIONS=1`, значением MSVC по умолчанию. Тогда `std::runtime_error` хранит
свою копию текста. Это две строки `CXXFLAGS_<цель>` в `.cargo/config.toml`, только для целей Windows MSVC.

`cc` ставит флаги окружения после своих `/D` как раз для того, чтобы они могли всё переопределить, а у `cl`
побеждает последний `/D`. `cc` следит за этой переменной, поэтому старые сборки в `target` пересоберутся сами.
Правка исправляет все 17 мест `throw std::runtime_error`, а не один `remove_track`.

Тест вызывает `remove_track` на закрытом соединении 1000 раз и не требует сервера. Без правки он падал три раза из трёх.

## Почему не на стороне OurCamp
SDK запускает закрытие сам, из своей задачи, сразу после события `Disconnected`. Снять дорожки заранее нельзя:
о разрыве мы узнаём, когда соединение уже закрыто, и наш `unpublish_track` прошёл бы по тому же пути.

## Отвергнутые варианты
- **Обновить SDK.** В `webrtc-sys` 0.3.52, новейшем на сегодня, `peer_connection.cpp` и `build.rs` не изменились, и
  он собирается с тем же `webrtc-sys-build` 0.3.21. Обновление не поможет.
- **Копия `webrtc-sys-build` с макросом в `IGNORE_DEFINES`.** Тоже работает, проверено, но это чужой крейт в
  репозитории, который придётся обновлять вместе с SDK. Настройка делает то же самое без копии.
- **`/U_HAS_EXCEPTIONS` через `CXXFLAGS`.** `/U` снимает только то, что определено раньше него, а здесь нужно
  задать значение. Проверено на примере с `/U` перед `/D`: значение остаётся 0.
- **`_CL_` в окружении.** `cc` за этой переменной не следит: старые сборки в `target` тихо остались бы с ошибкой.
- **`debug-assertions = false` для `cxx`.** Прячет проверку и оставляет чтение свободной памяти.
- **Своё исключение в копии `webrtc-sys`.** Копия намного больше, и правок было бы 17 вместо одной.

## Последствия
- Настройка работает только для сборок из этого репозитория, как и статический CRT из ADR-0012. Если `cc` когда-нибудь
  поменяет порядок флагов или в окружении будет свой `CXXFLAGS_<цель>`, тест на Windows упадёт.
- При каждой компиляции файла `cl` пишет предупреждение D9025 о замене значения. Cargo не показывает вывод чужих крейтов.
- Готовый `libwebrtc.lib` по-прежнему собран с `_HAS_EXCEPTIONS=0`, а `webrtc-sys` теперь со значением 1, как и
  `cxx.cc`, который собирался так всегда. Смешение режимов было и раньше, теперь граница проходит по готовой
  библиотеке. Исключения из неё к нам не летят: всё, что бросается, бросает `webrtc-sys`. Проверено прогонами ниже.
- Ошибка есть в самом LiveKit и затрагивает всех пользователей SDK на Windows. Настройку можно будет убрать, когда её исправят там.

## Проверка
Все прогоны на Windows, с настоящим LiveKit.
- **Без правки:** новый тест падал 3 раза из 3, тесты голоса с зондом — 2 раза из 4.
- **С правкой:** новый тест проходит. Все `#[ignore]`-тесты: 30 прогонов по одному и 60 параллельно, все зелёные.
- **Release** с настоящим профилем: новый тест и тесты голоса проходят.
- **Не проверено:** цель `aarch64-pc-windows-msvc`, настройка для неё задана по аналогии.

Вне этой правки: в 40 прогонах, которые шли ещё во время работы над ней, два теста по разу не дождались LiveKit:
`silencing_takes_the_mic_down_and_lifting_brings_it_back` (10 с) и `presence_is_seen_by_members_outside_voice` (3 с). Падений
процесса там не было, в следующих 90 прогонах это не повторилось, причина неизвестна.
