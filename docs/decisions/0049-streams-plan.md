# 0049. Стримы: захват SDK, аппаратный H.264 через Media Foundation, план M6

**Дата:** 2026-10-31 · **Статус:** принято · заменяет в [0008](0008-audio-quality-defaults.md) строку
«Видео стрима» (simulcast, 1080p60) и в [0002](0002-native-media-engine.md) выбор `scap` ·
**Код:** пока нет, это план M6

## Контекст
M6 — стримы, экраны 11 и 12 макета: окно «Начать стрим» (что показать, 720p/1080p, 30/60 fps,
«Транслировать звук») и окно просмотра (видео, LIVE, число зрителей, громкость стрима, на весь
экран). Прежний план: `scap` + аппаратный H.264 + simulcast.

## Что показала проба
На ПК Димы (RTX 3060, экран 2560×1440), LiveKit SDK 0.9.7:

| Вопрос | Ответ |
|---|---|
| Захват экрана в SDK (`DesktopCapturer`, WGC / DirectX) | 59,3 fps из 60, ≈1 мс на вызов, 0 сбоев |
| Кодеки в сборке | H264, VP8, VP9, AV1 — и отправка, и приём |
| Аппаратное кодирование в SDK на Windows | **нет:** NVENC и VAAPI собираются только под Linux (`webrtc-sys/build.rs`) |
| Кодировщики Windows | `NVIDIA H.264 Encoder MFT` (Media Foundation) и программный `H264 Encoder MFT` |
| Передача готового потока | есть: `NativeVideoSource::new_encoded`, `capture_encoded_frame`, запросы ключевых кадров и битрейта |
| Simulcast для готового потока | **нет:** `supports_simulcast = false` |

Ещё **не проверено**, это задача шага 1 и 3:
- что поток из Media Foundation проходит через LiveKit и декодируется у зрителя;
- что поверхность `wgpu` и веб-панель уживаются в одном окне.

## Решение
- **Захват — `DesktopCapturer` из SDK, без `scap`.** Экраны и окна, курсор. Меньше зависимостей,
  на Windows уже работает, на macOS (ScreenCaptureKit) и Linux (PipeWire) код общий.
- **Кодирование на Windows — своё, через Media Foundation:** кадр BGRA → NV12 → H.264 MFT →
  `capture_encoded_frame`.
  - MFT один для всех: NVIDIA, Intel и AMD ставят свой, программный есть всегда (и на раннерах CI).
  - Порядок выбора: аппаратный, затем программный; без кодировщика стрим не начинается и говорит почему.
  - Запросы ключевых кадров и битрейта от WebRTC идут в MFT.
  - Нужен крейт `windows` (COM) только под Windows: писать привязки COM самим нет смысла.
- **macOS и Linux — кодировщики SDK** (VideoToolbox, VAAPI/NVENC), обычные кадры. Windows идёт первым,
  на остальных системах сборка не ломается, а окно стрима включается после шага 6.
- **Качество одно, выбирает стример; simulcast нет.** Готовый поток его не поддерживает.

  | Качество | Битрейт |
  |---|---|
  | 720p30 | 2,5 Мбит/с |
  | 720p60 | 4 Мбит/с |
  | 1080p30 | 4 Мбит/с |
  | 1080p60 | 6 Мбит/с |

  Больше не масштабируем: источник сжимается до выбранного качества с сохранением пропорций.
- **Подписка по запросу.** Сейчас клиент подписывается на всё (`auto_subscribe`): с видео каждый
  участник канала качал бы каждый стрим. Подписка становится явной: микрофоны — всегда, стрим — пока
  открыто его окно.
- **Просмотр — окно на `wgpu`, снизу веб-панель.** I420 → шейдер, кадры не проходят через IPC
  (ADR-0002). Панель (имя, качество, громкость, на весь экран) — обычная веб-страница, рядом с
  видео, а не поверх: прозрачность WebView2 над чужой поверхностью ненадёжна. Значок LIVE и число
  зрителей рисуются в панели, не на видео, как в макете.
- **Кто в эфире:** сервер видит дорожку `SCREEN_SHARE` в опросе LiveKit и кладёт `streaming` в снимок.
  Значок LIVE видят все, даже вне голоса. Число зрителей — из атрибутов участников в комнате.
- **Смотреть можно только в своём канале.** Клик по LIVE в другом канале сначала переводит туда.
  Клиент держит одну комнату, а вторая ради просмотра усложнила бы всё и звук в том числе.
- **Звук стрима на Windows — WASAPI process loopback** с исключением своего процесса (Windows 10 2004+):
  в эфир идёт звук системы **без голосов собеседников**, иначе зрители слышали бы сами себя. Для окна —
  только звук его процесса. Opus стерео 128 кбит/с, `ScreenshareAudio`, у зрителя отдельный источник
  микшера со своей громкостью (стерео микшер уже умеет). Старше 2004 галочка неактивна.

## M6 по шагам
Каждый шаг заканчивается рабочим состоянием и проверкой в настоящем приложении (ADR-0047).

1. **Стрим без окон:** кодировщик MFT, захват → LiveKit → зритель получает кадры. Здесь проверяется
   главная гипотеза. Тест на настоящем LiveKit с синтетическими кадрами и программным MFT, замер CPU
   на настоящем экране.
2. **Подписка по запросу и LIVE:** `auto_subscribe` выключен, `streaming` в снимке, значок в дереве.
3. **Окно просмотра:** `wgpu`, панель, на весь экран, отключение подписки при закрытии.
4. **Окно «Начать стрим»:** список экранов и окон, качество, частота, кнопка «Стрим» в главном окне.
5. **Звук стрима:** process loopback, публикация, источник микшера, громкость.
6. **macOS и Linux:** кодировщики SDK, включение окон, чеклист.

## Отвергнуто
- **`scap`** — лишняя зависимость, SDK уже захватывает с нужной скоростью.
- **Программный кодировщик SDK на 1080p60** — занял бы несколько ядер во время игры.
- **Своя привязка к NVENC** — только NVIDIA; MFT покрывает и Intel, и AMD.
- **Аппаратный simulcast двумя кодировщиками** — SDK его для готового потока не принимает.
- **Видео через webview (canvas / WebCodecs)** — противоречит ADR-0002: кадры шли бы через IPC.
- **`cpal` loopback** — захватывает всё, вместе с голосами в OurCamp.

## Последствия
- Зритель со слабым каналом получит рывки: ниже качество для него одного SFU не отдаст. Лекарство —
  стример выбирает качество ниже. Вернуться к simulcast, если SDK его добавит.
- Домашний сервер раздаёт стрим каждому зрителю: 1080p60 и 3 зрителя — это 18 Мбит/с исходящего канала
  хозяина. Окно «Начать стрим» покажет это предупреждением на шаге 4.
- Крестик окна просмотра закрывает только просмотр, голос остаётся.
