# 0022. Свой LiveKit лагеря (`managed`): дочерний процесс под присмотром

**Дата:** 2026-10-28 · **Статус:** принято · реализует режим `managed` из [0016](0016-camp-server-shape.md) ·
**Код:** `crates/oc-server/src/livekit/`, `dev/fetch-livekit.ts`, `crates/oc-server/tests/managed.rs`

## Контекст
До шага 5 LiveKit жил отдельно — в Docker (`pnpm livekit`, ADR-0013), с ключом `devkey`.
Хозяину лагеря Docker не нужен: сервер лагеря должен сам поднять LiveKit, дать ему свой
ключ, перезапустить при падении и не оставить его висеть после себя.

## Решение
- **Режим по умолчанию — `managed`.** `--livekit-url ws://…` включает `external` (Docker);
  флаги режимов не смешиваются (`--livekit-key` без `--livekit-url` — ошибка).
- **Бинарник:** `--livekit-bin`, иначе рядом с `oc-server` (туда его положит установщик, M8),
  в `dev/bin` этого репозитория (только debug-сборка) и в `PATH`. Для разработки —
  `pnpm livekit:fetch`: та же версия, что в `dev/compose.yaml` (1.13.9), **SHA-256 каждого
  архива закреплены в скрипте**, а не берутся из `checksums.txt` релиза (подменённый архив
  пришёл бы со своим `checksums.txt`). Распаковка — системный `tar` (на Windows — свой
  `System32\tar.exe`, bsdtar: Git может подсунуть GNU tar, который читает `C:` как хост).
  У LiveKit нет релизного бинарника для macOS — там `brew install livekit`.
- **Ключ API** генерируется при первом старте (`OC` + 12 hex, секрет — 32 случайных байта
  в hex) и хранится в `<data>/livekit-keys.json` (атомарная запись, на unix `0600`):
  токены, выданные до перезапуска, остаются годными. Испорченный файл заменяется новым —
  ключ не покидает машину.
- **Конфиг и ключ — через окружение** (`LIVEKIT_CONFIG`, `LIVEKIT_KEYS`), не через командную
  строку, которую видят другие пользователи. Переменные LiveKit родителя (`LIVEKIT_*`,
  `NODE_IP`, `UDP_PORT`, `REDIS_*`) ребёнку не передаются — они переписали бы конфиг.
- **Порты:** сигнализация и API — **свободный порт на 127.0.0.1**, выбирается при старте
  (снаружи его видит только прокси `/rtc`, ADR-0019; не конфликтует с Docker на 7880).
  Медиа — фиксированные 7881/tcp и 7882/udp (их пробрасывают на роутере), флаги
  `--rtc-tcp-port`/`--rtc-udp-port`. `node_ip` — адрес из ссылок, если это IPv4; домен
  и IPv6 — на автоопределение LiveKit (внешний адрес — шаг 7, UPnP).
- **Готовность:** LiveKit принял TCP-подключение на порту сигнализации (до 20 с). Вышел
  раньше — ошибка старта с последней строкой его лога; занятые порты узнаются по тексту
  ошибки Go на обеих ОС → «порты заняты, `pnpm livekit:down`». (LiveKit при этом выходит
  с кодом 0, по коду не понять.)
- **Присмотр:** падение → перезапуск через 1 с, задержка удваивается до 30 с; прожил
  60 с — снова 1 с. `Running::stop` останавливает LiveKit последним, после API.
- **Не переживает лагерь, даже убитый без шанса на уборку:**
  - **Windows:** job object с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`; единственный дескриптор
    у сервера, ОС закрывает его у умершего процесса → LiveKit убит. Немного `unsafe` FFI
    через `windows-sys` (та же версия, что у tokio).
  - **unix:** LiveKit запускает сторож на `sh`, держащий pipe от сервера; EOF (сервер
    остановил или умер) → `SIGTERM`, через 2 с второй (LiveKit пропускает «дренаж»),
    через 3 с `SIGKILL`. Сторож же сообщает настоящий pid LiveKit первой строкой.
  - **Своя группа процессов** (`CREATE_NEW_PROCESS_GROUP` / `process_group(0)`): Ctrl+C
    в терминале получает только сервер и гасит LiveKit сам, по порядку. Иначе LiveKit
    выходил бы первым, а присмотр принимал бы это за падение. `CREATE_NO_WINDOW` — чтобы у
    окна сервера (шаг 6) не всплывала консоль LiveKit.
- **Лог LiveKit** идёт в лог сервера построчно с `[livekit]` (байтами, не `lines()`: битый
  UTF-8 не должен остановить чтение — иначе pipe заполнится и LiveKit встанет).

## Почему сторож на `sh`, а не `PR_SET_PDEATHSIG`
`PDEATHSIG` есть только в Linux (на macOS нет) и срабатывает при выходе **потока**,
создавшего ребёнка, а не процесса: ребёнок, запущенный из потока `spawn_blocking`,
погиб бы, когда пул уберёт простаивающий поток. Сторож — один механизм для Linux и macOS,
без `unsafe` и без зависимостей.

## Проверка
- Юнит-тесты: ключи создаются один раз, испорченные заменяются; конфиг; фильтр переменных;
  распознавание «порт занят» в формулировках Linux и Windows.
- `tests/managed.rs` (`#[ignore]`, нужен бинарник) с настоящим livekit-server: токен лагеря
  проходит `/rtc/validate` (значит, LiveKit доверяет сгенерированному ключу); после
  перезапуска лагеря ключ тот же; убитый LiveKit возвращается; бинарник `oc-server`,
  убитый `TerminateProcess`/`SIGKILL`, не оставляет LiveKit. Последний тест проверен
  мутацией: без job object он падает.
- Живость LiveKit в тестах — **подключением** к медиапорту, а не `bind`: LiveKit слушает
  `[::]` (оба стека), и Windows разрешает занять `0.0.0.0` рядом — `bind` ничего не доказывает.
- CI: задача `managed-livekit` на Ubuntu и Windows — clippy и тесты с бинарником из
  `node dev/fetch-livekit.ts`. macOS не проверяется: нет релизного бинарника.

## Отвергнуто
- **Конфиг-файл с секретом на диске** — лишний файл с секретом; окружение процесса видит только его
  владелец (и администратор).
- **Фиксированный порт сигнализации 7880** — конфликт с Docker-LiveKit и без пользы: его
  знает только сам сервер.
- **Бинарник в репозитории** — по 20 МБ на ОС (как и в ADR-0013).

## Последствия
- `pnpm server` и `pnpm livekit` вместе не работают (оба на 7881/7882): Docker остаётся
  для тестов голоса приложения и `pnpm server:docker`.
- Установщик (M8) кладёт livekit-server рядом с `oc-server`; для macOS его придётся
  собирать из исходников (Go) — в M8.
- Окно сервера (шаг 6) берёт `Running::livekit_pid()` и лог `[livekit]` для статуса.
